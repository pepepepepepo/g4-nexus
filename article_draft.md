## What I Built

[g4-nexus](https://github.com/pepepepepepo/g4-nexus) is a parallel persona engine built on Google's Gemma 4 models. Instead of asking one model one question, it asks **four specialized personas simultaneously** — then synthesizes their answers into a single integrated response.

The four personas:

| Name | Model | Role |
|------|-------|------|
| 🌕 Mochi  | gemma4:e2b | Emotion & empathy |
| 🗓️ Jun    | gemma4:e2b | Logic & expression |
| 🗝️ Uruu   | gemma4:e2b | Analysis & observation |
| 📅 Koyomi | gemma4:e4b | Integration leader |

> **Note:** `gemma4:e2b` and `gemma4:e4b` are the official [Ollama library tags](https://ollama.com/library/gemma4) for these models. "E" stands for "effective" parameters.

A single model gives you *an* answer. g4-nexus gives you:

- **Emotional grounding** (Mochi) — is the user overwhelmed? burned out?
- **Logical structure** (Jun) — what are the concrete steps?
- **Critical observation** (Uruu) — what context is missing? what assumptions are wrong?
- **Integrated action plan** (Koyomi) — what should they actually *do* right now?

This is useful for: decision support, design reviews, multi-stakeholder analysis, or just thinking through a hard problem from every angle at once.

**Safety note:** g4-nexus is not an autonomous or self-evolving system. It has no internet access, no persistent agency, and no capability to act outside answering questions. It is a local inference orchestration layer — explicit, inspectable, and fully under user control.

## How I Used Gemma 4

The choice of E4B (Effective 4B — ~4.5B total params) and E2B (Effective 2B — ~2.3B total params) was intentional:

> The "E" in E2B and E4B stands for **"effective" parameters** — optimized for edge device and local deployment.

**Why not the 31B Dense model?**
1. **Accessibility** — E2B/E4B run on consumer hardware without cloud costs. The 31B would require hardware most users don't have.
2. **Specialization** — Smaller models are easier to steer into a narrow role via system prompts. E2B workers stay in their lane (emotion, logic, analysis) reliably.
3. **Parallel speed** — Three E2B workers fit comfortably alongside the E4B leader. Running four 31B instances in parallel is not practical locally.

**Why two different model sizes?**

The leader (Koyomi, E4B) needs more capacity to hold and synthesize three separate reports. The workers (Mochi, Jun, Uruu, E2B) each handle a single focused task — smaller and faster is better there.

**The architecture: `asyncio.gather`**

Three E2B workers run **in parallel**, then the E4B leader integrates:

```python
async def run_tribe(user_message: str) -> dict:
    # Fire all 3 workers simultaneously
    worker_results = await asyncio.gather(
        ask_worker("mochi", MOCHI_SYSTEM, msg, WORKER_OPTIONS),
        ask_worker("jun",   JUN_SYSTEM,   msg, WORKER_OPTIONS),
        ask_worker("uruu",  URUU_SYSTEM,  msg, WORKER_OPTIONS),
    )

    # Leader receives all 3 reports and integrates
    combined = build_leader_prompt(worker_results)
    koyomi_response = await ask_leader("koyomi", KOYOMI_SYSTEM, combined, LEADER_OPTIONS)

    return {"workers": worker_results, "koyomi": koyomi_response}
```

This is **not** a chain. The workers do not see each other's answers — they work independently, in parallel, from the same user input. This is what Gemma 4's small, steerable models unlock: you can run multiple specialized instances simultaneously on a single consumer GPU.

On an RTX 4070 Ti (12GB VRAM) with 48GB system RAM: workers finish in ~9s, leader integrates in ~25s, **total ~31s**.
